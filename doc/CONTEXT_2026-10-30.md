## 1. Diagnóstico de arranque Docker

### Error resuelto: `DNS lookup failure for: api`
- **Causa:** El contenedor `api` estaba en un bucle de reinicio porque el valor de `JWT_SECRET_KEY` en `.env` era el valor de ejemplo: `tu_clave_secreta_de_al_menos_32_caracteres`.
- **Validación afectada:** `backend/config/load.py` línea 36: el validador de Pydantic rechaza claves que empiecen con `tu_` o tengan menos de 32 caracteres.
- **Solución:** Reemplazar el valor en `.env` con: `python -c "import secrets; print(secrets.token_hex(32))"`.

### Credenciales del admin predeterminado
- **Usuario:** `admin`
- **Contraseña:** `admincfs`
- **Rol:** `Administrador` (acceso total, `admin-g`)

## 2. Correcciones de seguridad y lógica de roles

### Bug 1 — Asignación errónea de rol elevado a usuarios normales
**Archivo:** `backend/api/usuarios.py`

La condición en línea 95 era `if data.es_admin_s or data.tipo == "tecnico":`.
Esto causaba que cualquier usuario con `tipo="tecnico"` recibiese el rol **Administrador de Sede** sin importar `es_admin_s`.

**Corrección:** Cambiar a `if data.es_admin_s:`. El rol solo se asigna cuando el flag llega explícitamente `True`.

### Bug 2 — Sin validación de unicidad de admin-s por sede
**Archivo:** `backend/api/usuarios.py`

No existía restricción para evitar múltiples `admin-s` en la misma sede.

**Corrección:** Se añadió una query previa dentro del bloque `if data.es_admin_s:` que consulta si ya existe un `Tecnico` con el rol `Administrador de Sede` para esa sede. Si existe, se lanza `HTTP 409 Conflict`.

## 3. Mejoras del frontend

Valida contra `/api/me` (renovando tokens vía `/api/refresh` si el token expiró) y redirige de forma inmediata al dashboard correspondiente (`home/usuario.html` o `home/index.html`) usando `replace()` para no entorpecer el historial del navegador.

## 5. Arquitectura de roles (actualizada)

```
admin-g  (Administrador General)
  └─ Acceso total a todas las sedes
  └─ Puede crear sedes, admin-s y usuarios en cualquier sede
  └─ Tipo ORM: TecnicoJefe (nivel_acceso=5)

admin-s  (Administrador de Sede)
  └─ Acceso exclusivo a UNA sede asignada
  └─ Puede crear únicamente usuarios_sede en su sede
  └─ UNO POR SEDE (unicidad validada en backend con HTTP 409)
  └─ Tipo ORM: Tecnico

usuario_sede  (Cliente / Usuario regular)
  └─ Acceso a servicios (chat, videoconferencia)
  └─ Sin acceso al panel de administración
  └─ Tipo ORM: UsuarioSede
```
